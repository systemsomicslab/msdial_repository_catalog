# Agent contract for MS-DIAL Class and contrasts

## Principle

There is no universally correct Class label for one public dataset. The useful
grouping depends on the scientific question. For example, age may be the primary
contrast in one analysis and a covariate in another.

The catalog therefore gives an agent a structured request generated by
`build_class_proposal_request()`.

## Required agent output

The response must contain:

- analysis purpose
- selected metadata fields in order
- one Class assignment for every sample
- source values used for each assignment
- rationale tied to repository fields
- explicit contrast definition
- warnings about missing, confounded, or study-level-only metadata

The output is rejected when samples are missing, duplicated, or invented.
Blank, QC, Standard, batch, pairing, and analytical order must remain available
as design metadata even when they are not part of Class.

## Review lifecycle

`proposed -> reviewed -> accepted` or `rejected`

The accepted proposal records model identity and prompt hash. Re-running an
agent creates a new proposal; it does not mutate the repository metadata or the
previous decision.

## MCP integration

The initial MCP surface exposes:

- `msdial_catalog_status`
- `msdial_catalog_search`
- `msdial_catalog_get_analysis_unit`
- `msdial_catalog_class_request`
- `msdial_catalog_save_class_proposal`
- `msdial_catalog_reanalysis_handoff`

The handoff never downloads raw data; the receiving MS-DIAL Interactive
workflow applies its own confirmation and size limits.

The search and inspection tools require no LLM. The proposal tool uses the LLM
only for a purpose-specific decision and must return evidence for review.
